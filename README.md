# Rougelike 隨機地圖生成器

## Proposal Report

### 動機與目標
Rougelike 遊戲對我來說的迷人點在於其過程的不可預測性，以及重複遊玩時每次都有不同體驗。  
本專案目的為設計一款 Rougelike 遊戲的隨機地圖生成器，方便在開發類似遊戲時可以使用，期望能製作一套能穩定生成合理、具挑戰性且不重複之地圖的系統  

### 競品比較
| 比較維度 | 本專案（Godot 隨機路線生成器） | 殺戮尖塔（原版遊戲地圖） | 市售通用地圖插件（Asset Store） |
| :--- | :--- | :--- | :--- |
| **核心目標** | **演算法實作與開源工具化** | 服務於單一遊戲體驗 | 商業化、大眾化 |
| **演算法透明度** | **極高**（專為展示資料結構設計，提供除錯視覺化） | **低**（封裝在遊戲底層，玩家無法得知運作邏輯） | **低**（多為編譯後的黑盒工具 / Black-box） |
| **參數自訂性** | **高**（可自由調整樓層數、節點密度、各類型生成權重） | **無**（數值與規則已寫死） | **高**（但通常伴隨過於複雜的 UI 與學習成本） |
| **圖論驗證機制** | **明確展示**（包含防死胡同、確保連通 Boss 的演算法展示） | 內部隱藏運算 | 通常只保證結果，不展示過程 |
| **引擎依賴性** | **原生 GDScript**（輕量，可直接嵌入任何 Godot 專案） | 無法提取 | 依賴特定版本引擎，有時會造成專案臃腫 |

### 預期功能
參考遊戲《殺戮尖塔》的地圖設計，採用節點式的地圖，給予玩家策略選擇權。
1. 確保地圖路線可行性，防止生成出不合理或無法使用的地圖。
2. 建立節點屬性的分配規則（如：戰鬥、菁英、事件、商店、營地），並能自訂權重，防止生成極端不平衡的路線（例如連續三個營地）。
3. 控制節點分配與路線連接，確保視覺上清晰易讀，不會產生過於混亂的交叉線條。

### 使用技術
預計使用 Godot 當作主要的開發引擎，因為其內建的節點系統非常好用，可以方便快速打樣與實作，也方便視覺化。  
搭配的程式語言是 GDScript，為 Godot 官方的推薦語言。  
核心演算法主要會用到 DAG 的生成，以及在驗證走法時會用到 DFS/BFS 的走訪。

### Prototype 預計可驗證內容
1. 底層邏輯與連通性驗證
- 驗證目標： 確保生成的資料結構符合嚴格的「有向無環圖（DAG）」。
- 可驗證內容：
  - 生成器能穩定輸出不包含迴圈的路線圖，玩家絕對無法走回頭路。
  - 透過DFS演算法，證明底層的每一個「起點」節點，必定存在至少一條路徑能抵達最頂層的「Boss」節點，且圖中沒有任何孤島節點。

2. 視覺化佈局與防交叉驗證
- 驗證目標： 確保抽象的圖論資料能轉換為清晰易讀的使用者介面。
- 可驗證內容：
  - 能在 Godot 畫面上成功繪製出帶有隨機偏移的節點陣列，呈現自然的佈局。
  - 展示「交點最小化」演算法的效果：在多次生成測試中，連接不同節點的線段不會產生嚴重的互相交叉與重疊，維持畫面的整潔。

3. 規則約束與權重驗證
- 驗證目標： 證明演算法能受到自訂規則的有效約束。
- 可驗證內容：
  - 改變輸入參數（例如將「營地」生成機率調高），地圖能即時反應新的機率分佈。
  - 驗證「極端規則防呆」是否生效：例如設定「連續兩層不可出現營地」或「第一層必定是普通戰鬥」，在 Prototype 中連續生成 100 次地圖，皆不會出現違反上述規則的錯誤路線。

4. 基礎互動性驗證
- 驗證目標： 確保資料結構能正確回應玩家的操作。
- 可驗證內容：
  - 玩家點擊某個起點後，系統能正確判定並高亮其「相鄰的下一層節點」。
  - 系統能封鎖無效操作，玩家無法點擊未相連的節點或跳層推進。

## Prototype Report

### 目前進度

本階段已完成一套可執行的 Roguelike 節點式隨機地圖生成原型，涵蓋「生成、驗證、互動、評估」四個層面，並可直接在 Godot 中進行操作與觀察。

目前已完成內容如下：

1. **地圖生成核心完成（DAG）**
   - 採用分層節點結構，連線僅允許由下層到上層，確保玩家無法回頭。
   - 每層節點數可隨機生成（中間層多節點，最終層固定 Boss）。
   - 連線時加入交叉抑制策略，降低視覺混亂。

2. **節點類型與規則約束完成**
   - 節點類型以權重分配：`combat / elite / event / shop / camp`。
   - 固定規則：第一層必為 `combat`、最後一層必為 `boss`。
   - 防呆規則：避免連續兩層 `camp`。

3. **連通性驗證完成**
   - 使用 DFS 驗證起點可達 Boss，避免無法完成的地圖。
   - 同時檢查是否有孤立或不合理的節點結構。

4. **互動式地圖操作完成**
   - 玩家可逐層點選合法節點前進。
   - 系統會封鎖不合法操作（跳層、未連線節點）。
   - 視覺上可辨識目前可選節點、已走路徑、已放棄路徑。

5. **地圖評分系統完成（體驗導向）**
   - 評分指標包含：
     - `choice_quality`（選擇品質）
     - `branch_options`（分支數量）
     - `path_diversity`（路徑多樣性）
     - `encounter_variety`（遭遇多樣性）
     - `pacing_balance`（節奏平衡）
   - 評分以 0~100 顯示，並持續保留於 UI，方便比較不同生成結果。

---

### 遇到的困難

目前主要困難已從單點程式問題，轉向「使用體驗」與「地圖在開發中可用性」：

1. **評分數值與實際遊玩感受尚未完全對齊**
   - 現有量化指標可描述地圖特徵，但仍需進一步校準，讓「高分」更穩定對應到「有趣、可策略選擇」的體驗。

2. **分支多不一定代表決策有價值**
   - 某些地圖雖有多分支，但路線差異不足，玩家會感覺選擇意義不大。
   - 如何提升分支之間的風險/回報差異，是目前待解決問題。

3. **節奏穩定性仍有波動**
   - 部分地圖在某些區段節點密度過高或過低，影響探索與戰鬥節奏。
   - 需要更穩定的 pacing 控制，避免局部過度平淡或過度擁擠。

4. **原型已可展示，但距離開發工具化仍有落差**
   - 目前偏向 demo 與驗證；若要貼近實務開發，仍需補上批次分析、參數管理、與內容系統串接等能力。

### 使用的演算法、資料結構、數學方法（詳細說明）

#### 1. 資料結構

1. **有向圖（Directed Graph）/ DAG**
   - 地圖本質是圖：節點為地圖事件點，邊為可移動路徑。
   - 透過「只連到上層」的規則使其成為 DAG。

2. **Adjacency List（鄰接串列）**
   - 每個節點保存：
     - `next`：可前往節點
     - `prev`：前置節點
   - 優點：便於 DFS/BFS、規則檢查與路徑統計。

3. **分層容器（Array of floors）**
   - 以樓層陣列管理節點集合，讓生成與驗證都可在明確拓樸順序下進行。

4. **Dictionary 快速索引**
   - 以 `node_id -> node_data` 做 O(1) 存取，方便在互動與評分過程頻繁查詢。

---

#### 2. 演算法

1. **分層 DAG 生成**
   - 先建立每層節點，再建立跨層邊。
   - 單向跨層保證無環，並可自然限制玩家只能往前推進。

2. **加權隨機抽樣（Weighted Random Sampling）**
   - 節點類型依權重決定。
   - 方法：累積權重 + 隨機落點選擇，並可在規則限制下動態移除禁用類型。

3. **DFS 可達性驗證**
   - 從起點做 DFS，驗證是否可達 Boss。
   - 用於確保地圖不是「看起來可玩但實際卡死」。

4. **路徑數計算（DFS Path Counting）**
   - 統計起點到 Boss 的路徑數，作為多樣性評估依據。

5. **交叉抑制啟發式**
   - 連線時優先接近欄位，並避免造成明顯交叉，提高可讀性。

---

#### 3. 評分模型

1. **加權總分模型**
   - 將子指標映射到 0~100 後，以權重加總：
   $$
   Score = \sum (\alpha_i \cdot m_i),\ \sum \alpha_i = 1
   $$
   - 目前偏重「選擇感」與「多樣性」。

2. **正規化（Normalization）**
   - 不同量綱指標（分支數、路徑數、比例）先統一到 0~100，避免某一指標天然主導總分。

## Final Report

### 專案說明

#### 📌 完整功能概述

本專案成功實現了一款**完整的 Roguelike 隨機地圖生成系統**，包含三種演算法實現、視覺化互動界面、以及完善的評分系統。整個系統可直接在 Godot 引擎中運行，並能穩定生成多樣化的遊戲地圖。

**核心成就：**

1. **三種演算法實現與比較**
   - **DAG（有向無環圖）算法** - 基礎實現，採用分層結構與交叉抑制
   - **BSP（二分空間分割）算法** - 遞迴分割空間，自然形成聚集分佈
   - **Forest（隨機森林）算法** - 結構化多路徑設計，提升決策品質與路徑多樣性
   
   三種演算法各有特色，用戶可在 UI 中實時切換並觀察差異，充分展示了不同演算法的設計理念與實現方式。

2. **圖論與資料結構應用**
   - **有向無環圖（DAG）** - 確保路線單向性，玩家永不回頭
   - **鄰接串列** - 高效儲存節點連接關係，支援 O(1) 邊查詢
   - **DFS 可達性驗證** - 保證每條起點路線必能抵達 Boss
   - **線段交叉檢測** - 採用 cross product 幾何演算法，減少視覺混亂

3. **節點類型與規則約束系統**
   - 6 種節點類型：戰鬥(Combat)、精英(Elite)、事件(Event)、商店(Shop)、營地(Camp)、Boss
   - 加權隨機抽樣實現靈活的類型分配
   - 防呆規則：
     - 第一層固定為 Combat
     - 最後一層固定為 Boss
     - 避免連續兩層 Camp 節點
     - 支援自訂規則（必定經過 Shop、Boss 前固定 Camp）

4. **互動式地圖遊玩系統**
   - 玩家逐層點選合法節點推進
   - 系統實時高亮可選節點，視覺化已走路徑與放棄路徑
   - 防止不合法操作（跳層、未連線節點選擇）
   - 完整流程驗證，確保邏輯正確

5. **多維度評分系統**
   - **選擇品質**（Choice Quality）- 決策點比例評估
   - **分支數量**（Branch Options）- 平均出度指標
   - **路徑多樣性**（Path Diversity）- 路徑數目的對數正規化
   - **路徑品質**（Path Quality）- 路徑間差異度評估
   - **遭遇多樣性**（Encounter Variety）- 節點類型分布熵計算
   - **節奏平衡**（Pacing Balance）- 層級間節點密度穩定性
   
   評分以 0~100 統一量綱，加權合併呈現總分，方便不同地圖之間的比較。

6. **批次測試與統計分析**
   - 支援連續生成 1~1000 張地圖
   - 自動計算各項指標的平均值、標準差、極值
   - 演算法對比測試，量化展示不同演算法的優勢與劣勢
   - 種子碼系統保證結果可重現

#### 🔧 技術亮點

**演算法創新：**
- DAG 實現中的交叉抑制啟發式，在保證連通的前提下最小化視覺混亂
- BSP 通過遞迴空間分割實現自然聚類，區域化呈現地圖佈局
- Forest 通過多主路徑 + 分支點 + 跨路徑連接，在結構清晰與多樣性之間取得平衡

**工程設計：**

- 基類 MapGeneratorBase 定義統一介面，確保子類實現的一致性
- 評分系統採用模組化設計，各指標獨立計算，方便權重調整與擴展

**視覺化與互動：**
- 自訂字體加載（NotoSansTC）解決 HTML5 環境中文亂碼問題
- 多層次視覺反饋：節點懸停效果、邊著色區分、路徑高亮顯示
- 實時 UI 參數調整，無需重啟即可觀察變化效果

#### 🎯 課程關聯深度分析

**資料結構部分：**
1. **圖論與 DAG**
   - 項目核心是有向無環圖的實現與應用
   - 從零實現圖的生成、連接、驗證全流程
   - DFS 算法用於可達性驗證，確保遊戲邏輯正確性

2. **樹結構**
   - BSP 演算法採用遞迴分割樹，每次遞迴產生二叉樹結構
   - 樹的深度控制與節點聚集特性的實踐應用

3. **鄰接串列**
   - 每個節點儲存 next/prev 陣列，典型的鄰接串列表示
   - 支援 O(1) 邊查詢、便於 DFS/BFS 遍歷

4. **雜湊表（Dictionary）**
   - 以 node_id -> node_data 做快速索引，達到 O(1) 查詢
   - 路徑計數中使用 visited 集合追蹤已訪問節點

**進階程式設計部分：**
1. **設計模式**
   - 工廠模式（Factory）統一管理演算法建立
   - 策略模式（Strategy）選擇不同生成演算法
   - 模板方法模式（Template Method）定義基類介面

2. **物件導向設計**
   - 類繼承：MapGeneratorBase 基類，三個子類各自實現
   - 多態：统一的 generate_map() / verify_connectivity() 介面
   - 封裝：內部實現細節隱藏，對外提供清晰的方法簽名

3. **遞迴算法**
   - DFS 遞迴實現路径計数、可達性驗證
   - BSP 空間分割採用遞迴分治思想
   - 驗證正確性（無限遞迴防護、深度限制）

4. **加權隨機抽樣**
   - 實現累積權重 + 隨機落點選擇
   - 支援動態移除禁用選項（如禁止連續 Camp）
   - 應用於節點類型分配、演算法選擇等

5. **幾何計算與線段交叉檢測**
   - 採用 cross product 判斷兩線段相交
   - 優化視覺佈局，降低線段混亂度

**功能驗證：**
- ✓ 連通性驗證：所有起點都能抵達 Boss（DFS 前/後向遍歷）
- ✓ 無環驗證：分層結構保證單向性
- ✓ 規則約束：連續 Camp 防呆、類型分配符合權重

#### 📋 測試與驗證

**自動測試流程：**

1. **運行時驗證**
   - 每次生成地圖後，自動執行 `verify_connectivity()`
   - DFS 驗證確保所有起點可達 Boss
   - 若驗證失敗顯示 "FAIL" 標記（紅色），通常不會發生

2. **批次測試**
   - 在 UI 中設定測試數量（建議 50~100）
   - 點擊「執行演算法對比測試」
   - 系統連續生成，逐個評分，最後匯總統計

3. **手動測試**
   - 點選節點逐層推進，驗證邏輯正確性
   - 嘗試點擊不合法節點，系統應拒絕
   - 調整參數觀察地圖變化

#### 🐛 常見問題與解決

**Q1: 運行時提示「字型加載失敗」**
- A: 確保 `NotoSansTC-Regular.ttf` 檔案在專案根目錄，否則會自動降級為預設字型

**Q2: 生成的地圖無法連通（顯示 FAIL）**
- A: 這不應發生，如若遇到請檢查：
  - 演算法是否正確繼承 MapGeneratorBase
  - verify_connectivity() 邏輯是否正確實現
  - 首層與尾層節點是否正確建立

**Q3: 評分異常高/低**
- A: 檢查評分權重配置（map_evaluator.gd 第 4 行）
  - 若要調整，修改 METRIC_WEIGHTS 字典即可

**Q4: 批次測試速度很慢**
- A: 這是正常的，視電腦性能而定
  - 生成 1000 張地圖通常需要 3-10 秒
  - 可用 Godot 的 Profiler 工具監測性能

#### 🚀 進階使用

**自訂演算法：**

1. 建立新文件 `map_generator_custom.gd`
2. 繼承 `MapGeneratorBase`
3. 實現 `generate_map()` 和 `verify_connectivity()`
4. 在 `main.gd` 中的演算法選擇處新增選項

**調整評分權重：**

編輯 `map_evaluator.gd` 中的 `METRIC_WEIGHTS`：
```gdscript
const METRIC_WEIGHTS := {
    "choice_quality": 0.25,       # 提高決策品質權重
    "branch_options": 0.15,
    "path_diversity": 0.20,
    "path_quality": 0.15,
    "encounter_variety": 0.15,   # 降低多樣性權重
    "pacing_balance": 0.10
}
```
